A hexagonal collector behind a single-owner core: three scrapers through one SourcePort, one filter-chain pipeline, one SQLite writer, one JSON envelope — ten decisions (AD-1…AD-10) keeping a two-process localhost system coherent.

00

Context & thesis

A personal job-hunt tool for Akram: aggregate Google Jobs, ouedkniss and Facebook groups into one local view — with the pipeline patterns of his ouedkniss real-estate platform, and the discipline of one database owner. Judgment over coverage: the point is not collecting more, it is deciding faster on cleaner, fresher data.

COVERAGE IS FUEL

Three messy sources, one port

Google Jobs via JobSpy, ouedkniss via a bespoke Scrapy spider, Facebook groups via Playwright — each mapped to one fixed canonical field set at the SourcePort (AD-1). Adding a site is an adapter plus a registry row; reusing one is a row only.

JUDGMENT IS THE PRODUCT

The 24-hour window

Dedupe and freshness flags mean apply decisions happen while openings are hot. Cross-posting footprint (AD-8) is urgency for free, and apply outcomes are captured now so v2 scoring (FR-6…8) needs no new collection.

ONE OWNER, NO DRIFT

Everything through Django

Adapters and the frontend are both outsiders. All writes go through the Django app; schema changes exist only as migrations; two processes serialize at SQLite via WAL + busy_timeout (AD-2).

“One invariant does most of the work: everything that touches the database goes through the Django app — adapters and the frontend are both outsiders.”

Decisions — AD-1 … AD-10

Ten decisions, one spine. Each card shows what the decision binds, what it prevents, and the rule that holds — every assumption is flagged. Click a card to expand it.

AD-1

The SourcePort extension contract

FR-1FR-2FR-5 collection
▾
BINDS

FR-1 · FR-2 · FR-5 — all collection.

PREVENTS

Core edits per new site; adapter-specific logic leaking into the core or the DB.

RULE

Every Source is an adapter implementing SourcePort: fetch(keywords) → raw items; parse() → canonical field set — plus one row in the Source Registry (name, adapter key, config). The canonical field set is fixed: title, company, url, published_at (ISO-8601 UTC), keywords, raw_snapshot. Adapters map site structure into canonical fields; cross-source value harmonization (salary units, date formats, location strings) belongs to the pipeline's normalize stage (AD-3) — never to adapters. Adding a site = new adapter + registry row; reusing a registered adapter = registry row only, no code change. Adapters may not import each other or touch the DB.

ASSUMPTION — Resolution of PRD OQ1: code-first adapters (a Python module per site); YAML-only configs deferred. User approval pending — the PRD FR-1 consequence (“without code changes”) is to be amended.

AD-2

Single owner of persisted state

ALLcross-cutting
▾
BINDS

All FRs.

PREVENTS

Two writers (frontend vs collector) drifting the schema; direct DB access from Next.js.

RULE

The Django app is the only writer to SQLite; all writes go through Django ORM/services — adapters and the Next.js frontend included. Next.js reads and issues commands only via the JSON API. Schema changes exist only as Django migrations. The two local processes (Django server + collector worker) both write via the ORM; SQLite runs in WAL mode with busy_timeout set so interleaved writes serialize at the DB, not in app logic.

ASSUMPTION — WAL + busy_timeout are the whole locking story for a single-user localhost load.

AD-3

Pipeline stages are pure filters

FR-2collection
▾
BINDS

FR-2.

PREVENTS

Pipeline stages coupling to each other or to storage.

RULE

Extraction, cleaning, and normalization are pure transforms (raw item → canonical fields). Boundary: adapters map site structure into canonical fields (AD-1); the normalize stage harmonizes values across sources (salary units, date formats, location strings). Only deduplication and validation consult the database, through a thin repository interface.

ASSUMPTION — repository = Django ORM queries wrapped in a ListingRepository service class.

AD-4

Listing identity and idempotent upsert

FR-2FR-3browse + apply
▾
BINDS

FR-2 · FR-3.

PREVENTS

Duplicate Listings across Sources; re-collection creating duplicates; collection clobbering application state.

RULE

Canonical Listing entity: title, company, url, source, published_at, keywords, raw_snapshot, status, dedup_fingerprint. dedup_fingerprint = hash of normalized(title) + company + url host — computed once at ingestion and immutable thereafter; it is never part of an upsert and never updates. An incoming item whose fingerprint exists updates only content fields (title, company, url, published_at, keywords, raw_snapshot) via atomic get-or-create; it never touches status, seen_sources, or dedup_fingerprint. status changes only through explicit services (the apply action; later, expiry). seen_sources is append-only — cross-posting footprint is derived from it, never overwritten. The fingerprint carries a DB unique constraint so concurrent collection passes cannot insert duplicates.

AD-5

Application uniqueness

▾
BINDS

FR-5.

PREVENTS

Double-apply records.

RULE

One Application per Listing — DB unique constraint on listing_id; marking applied is idempotent. An Application stores outcome (response / interview / silence — v2 field, nullable in v1) so FR-8's feedback loop needs no migration.

AD-6

Failure isolation per Source

FR-2collection
▾
BINDS

FR-2.

PREVENTS

One broken Source halting collection.

RULE

Each adapter fetch runs in its own error boundary: malformed or empty fetches are logged as FetchLog entries and never stop other Sources. Every persisted Listing keeps its raw snapshot for selector repair.

AD-7

Collection cadence and backfill

FR-2FR-3FR-4collection
▾
BINDS

FR-2 · FR-3 · FR-4.

PREVENTS

Missed polls without catch-up — the “24-hour window” value prop.

RULE

A collector worker polls all Sources every 30 minutes via APScheduler. After downtime, the next pass backfills missed polls and marks Listings older than 24 hours with a freshness flag.

AD-8

Cross-source dedup feeds Urgency Signals for free

FR-2FR-7 v2collection
▾
BINDS

FR-2 · FR-7 (v2).

PREVENTS

A second v2 pipeline that duplicates collection data.

RULE

The dedup stage records cross-posting footprint (same normalized role seen on N Sources) and deletion events in the Listing history; v2 Urgency Signals (FR-7) are queries over this data, not new collection.

ASSUMPTION — history = timestamps + a seen_sources set per Listing; deletion events from absent-in-next-fetch detection.

AD-9

Listing order, paging, and the new bucket

FR-3FR-4browse + apply
▾
BINDS

FR-3 · FR-4.

PREVENTS

Two builders choosing incompatible sort keys, page shapes, or bucket definitions for the same view.

RULE

Listings sort newest-first by published_at DESC, id DESC — tie-break stable across pages and days. Page size is 25. The “new since last visit” bucket is defined server-side: the app records last_sweep_at on the sweep view; a Listing is “new” while published_at > last_sweep_at and status is not applied.

ASSUMPTION — single-user means one server-side timestamp suffices; no per-device tracking.

AD-10

JSON API contract

FR-3FR-4FR-5browse + apply
▾
BINDS

FR-3 · FR-4 · FR-5.

PREVENTS

Frontend/API ambiguity — envelope shape, idempotency semantics, identifier location.

RULE

DRF-style JSON API with envelope {ok: bool, data: … | error: {code, message}}. Listings and Applications are addressed by listing ID in the path. POST /listings/<listing_id>/apply is idempotent: it returns 200 with the existing Application record when one exists (no 409). Timestamps serialize as ISO-8601 UTC. Next.js consumes only this envelope.

04

Roadmap — v1 now, v2 later, nothing invented

v1 ships the engine and the application loop. v2's scoring and signals ride on data v1 already captures — the spine's hooks are query and field, not new collection.

V1 — NOW

The engine + loop

FR-1 … FR-5 · the whole build-substrate scope
  • FR-1Register + test a Source — adapter + registry row
  • FR-2Collect + pipeline — raw → validate, 30-min polls
  • FR-3Browse Listings — newest-first, page of 25, “new” bucket
  • FR-4Detail + apply action — idempotent
  • FR-5Record Application — one per Listing, outcome nullable
  • Deployment envelope: one Windows machine, two processes — Django server + collector worker. No auth, localhost. The APScheduler loop is v1's “real-time.”
V1.5 — HOOKS

Hardening, not scope

deferred, cheap to revisit
  • Notifications / real-time push — frontend polls for now
  • LinkedIn source — ban risk on a personal account; revisit with a dedicated-account option
  • google-jobs resilience — proxy / SERP-API fallback; AD-6 already isolates its failures
  • YAML-only adapter configs — code-first adapters win for now (OQ1 resolution)
V2 — DEFERRED

Signals & scoring

FR-6 … FR-8 · data already captured
  • FR-6Interest Score — hand-maintained profile, rule-based heuristics; LLM parsing later
  • FR-7Urgency Signals — queries over Listing history (AD-8); no new collection
  • FR-8Feedback + pacing — rides the AD-5 outcome field, nullable in v1
  • Keyword + outcome data is captured from day one — v2 needs no migration for the loop.
LATER / NEVER-AT-THIS-ALTITUDE Dashboard & analytics (v2+); social & viral engines — engine generality unexercised; Postgres only if this ever leaves localhost; auth / multi-user / hosting — localhost single-user forever.
