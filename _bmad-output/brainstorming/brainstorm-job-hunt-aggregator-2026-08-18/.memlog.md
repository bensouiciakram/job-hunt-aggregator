- (technique) started SCAMPER Method (7 lenses)
- (idea) Substitute: aggregate activity signals around a job post (views, app count, post age, recruiter activity) instead of raw posts
- (idea) Substitute: match on industry/problem the recruiter is solving instead of keywords
- (idea) Substitute: automation stack = scrapy + playwright + LLM-based parsing instead of raw HTML parsing
- (idea) Substitute: recruiter reputation + recruiter engagement intensity on a post as the top signal (acknowledged hard to measure from outside)
- (idea) Proxy: how many websites the same recruiter posts the same job on (cross-platform footprint)
- (insight) Cross-posted job = recruiter in dire need of filling the role (urgency signal)
- (insight) Persistent scraping gives history: repost-pattern (same title/text reappears after delete) = churn signal; cluster of new related roles = growth signal — works on sparse platforms
- (technique) SCAMPER lens 1/7 Substitute done, moving to Combine
- (idea) Combine: scraper muscle + dev skills fusion = self-tuning filter — backend tracks application outcomes (response/interview/silence), learns which postings respond to profile, steers next fetch toward what works (user: very good idea to implement)
- (technique) SCAMPER lens 2/7 Combine done, moving to Adapt
- (idea) Adapt: entire scraping toolkit is reusable — can source any data the app needs without user input; existing medium projects: dz leads finder + algerian real estate analytics platform
- (idea) Adapt: reuse multi-phase pipeline from real estate platform (ouedkniss scraper, Fiverr-era) — rawListing > extraction > cleaning > normalization > deduplication > validation > analytics dashboard
- (direction) User recalibrated: keep questions practical — goal is easy access to opportunities + insight about new and old postings, not deep pipeline theory
- (idea) Interest signals: (1) requirements/tech stack matches user's stack, (2) company's problem type already solved in user's previous works, (3) post well-written with realistic expectations (no absurd stacked requirements)
- (decision) Scoring weights: problem-domain overlap and post sanity favored over tech-stack overlap
- (technique) SCAMPER lens 3/7 Adapt done, moving to Modify
- (idea) Modify: real-time (websockets/polling from Django scraper loop), paged full-list view, local web app (Next.js + Django), browser notification one-click actionable -> opens local job detail page with Mark-as-applied button next to external link
- (technique) SCAMPER lens 4/7 Modify done, moving to Put-to-other-use
- (idea) Put-to-other-use: same engine repurposed to monitor social media traffic/activity
- (idea) Put-to-other-use: detect products going viral in a region (trending product categories, not tracking individual products)
- (technique) SCAMPER lens 5/7 Put-to-other-use done, moving to Eliminate
- (decision) Eliminate: first version = job listings + easy add-new-site extensibility only; cut dashboards, tracking, feedback loop, LLM parsing, notifications
- (technique) SCAMPER lens 6/7 Eliminate done, moving to Reverse
- (idea) Reverse: the tool tells the user when to STOP (e.g., 10 great matches applied this week -> rest), sanity/anti-burnout mode
- (decision) Impact-Effort verdicts: 1 core engine (impact low / effort high) 2 listing UX (low/med) 3 interest scoring (high/med) 4 urgency signals (high/med) 5 application loop (high/LOW) 6 other uses (low/high)
- (decision) Locked direction: build order = simple extensible engine skeleton + application loop first, then interest scoring + urgency signals; principle: engine starts simple, designed to be extended
- (insight) Synthesis: (1) urgency signals = queries over persistent engine data, free once engine exists; (2) scoring = the product (judgment no job board offers); (3) self-tuning filter and stop-signal are one feedback mechanism; (4) put-to-other-use proved engine is generic - jobs are first client
